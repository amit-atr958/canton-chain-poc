# No-Docker / Hosted-Sandbox Feasibility Research

**Bottom line (as of 2026-09-16): not feasible.** There is no publicly reachable, open-signup Canton Network "DevNet"/"TestNet"/sandbox that a Node.js/React developer can point a Ledger API client at with just `npm install`. Every hosted Canton environment (DevNet, TestNet, MainNet) requires *running your own validator node* (or paying a third-party operator to run one for you) that is allowlisted and sponsored by a Super Validator (SV) — this is infrastructure at least as heavy as LocalNet, typically Docker/Kubernetes-based, plus a multi-day/multi-week human approval process. The official `cn-quickstart` project itself **removed** DevNet connectivity in July 2025 and now only documents LocalNet. Separately, and independent of hosting: this PoC's design requires a *custom* Daml template (`Compliance.daml` / `Token.daml` / `Transfer.daml`), and compiling a custom DAR requires the local Daml SDK (JDK-based `dpm`/`daml build`) no matter where the resulting DAR is later uploaded — there is no browser-based or hosted Daml build service. The practical recommendation is to keep Docker for the ledger (LocalNet, as the existing plan already does) rather than chase a hosted no-Docker path that doesn't exist yet.

## 1. All "Choose Your Path" paths — which need Docker?

The page (`docs/superpowers/specs/2026-09-15-canton-token-poc-design.md` already cites it) presents four audience-based tracks, all converging on the same hands-on modules and local tooling:

1. **"I'm new to blockchain development"** → Five-Minute Overview → Core Concepts → Module 1 → Module 3 (Daml Smart Contracts) → Module 4 (Building Applications).
2. **"I have Ethereum/Solidity experience"** → adds [Canton for Ethereum Developers](https://docs.canton.network/appdev/modules/m2-canton-for-ethereum-devs) and [Privacy Model](https://docs.canton.network/overview/learn/privacy-model) before the same Module 3/4 track.
3. **"I have experience with other blockchains"** → [Architecture Overview](https://docs.canton.network/overview/learn/architecture) then Module 3.
4. **"I want to understand Canton without coding"** → documentation-only track (Five-Minute Overview, The Problem, Canton's Solution, Use Cases, Architecture Overview) — no local infrastructure at all, but also no hands-on app.

[choose-your-path](https://docs.canton.network/appdev/get-started/choose-your-path)

**All coding paths converge** on the same prerequisites page, [`/appdev/quickstart/prerequisites`](https://docs.canton.network/appdev/quickstart/prerequisites), which requires local **Docker Desktop**, **Nix**, **direnv**, **curl**, and WSL2 on Windows — i.e., the QuickStart (which is `cn-quickstart`) is "a Dockerized application and requires Docker Desktop." The only path with zero local install is path 4, which is non-technical/conceptual only and does not build anything. **No path in this doc is "hosted/remote with no Docker."**

## 2. Is there a hosted Ledger API a Node/React app can call with zero local ledger process?

Short answer: **no**, not one reachable via open signup.

- The docs' own index describes three networks: `MainNet` (production), `TestNet` (production staging), and `DevNet` (development staging), and states plainly: **"Access to a SV Node that is whitelisted on the CN is required to connect to DevNet"** and to "contact your sponsoring SV agent for VPN connection information" [docs.canton.network/llms.txt](https://docs.canton.network/llms.txt).
- Reaching DevNet/TestNet/MainNet means **standing up your own validator node** (Splice validator app), which the Splice docs describe as deployed via **"docker compose or Kubernetes"** [Validator Onboarding — Splice docs](https://docs.dev.sync.global/validator_operator/validator_onboarding.html), plus completing an SV-sponsored allowlisting process that a Canton Network forum thread and third-party summaries describe as: DevNet requires your validator's egress IP on an SV-maintained allowlist (**reset every 3 months**); TestNet additionally requires tokenomics-committee approval and a one-time onboarding secret (**reset every 3–6 months**) [forum.canton.network — "How to run a validator on devnet?"](https://forum.canton.network/t/how-to-run-a-validator-on-devnet/8334), [Canton Foundation — Validators](https://canton.foundation/validators/), [canton.network blog — "How to get started with a validator"](https://www.canton.network/blog/how-to-get-started-with-a-validator-on-canton).
- The official quickstart used to bridge to a hosted DevNet but **no longer does**: the `cn-quickstart` README states verbatim, **"On July 2, 2025, the quickstart underwent an architectural change and no longer connects to DevNet"** [github.com/digital-asset/cn-quickstart](https://github.com/digital-asset/cn-quickstart) — direct evidence that the hosted-DevNet-for-quickstart-apps path existed and was discontinued.
- A third-party (not Digital Asset/Canton Foundation first-party) operator, **Canton Nodes** (run by Proof Group, "a premier investment firm and Super Validator on Canton"), advertises a free, rate-limited public Ledger API endpoint at `https://api.cantonnodes.com` — but this is documented only for **MainNet**, not DevNet/TestNet, is third-party infrastructure, and is rate-limited [cantonnodes.com](https://www.cantonnodes.com/). Because it's MainNet, using it for a PoC means real network fees and no faucet, and it is not a place to freely upload arbitrary custom DARs.
- "Daml Hub" (Digital Asset's older managed cloud Daml service) still appears active in Digital Asset's own release notes as of mid-2024 (PQS/Participant/Synchronizer Services promoted to GA) rather than retired, but it targets classic Daml Ledger/participant hosting, not the Canton Network global-synchronizer/Splice stack this PoC targets, and no current doc links it from the Canton Network "Choose Your Path" or wallet-integration docs — it is not a path forward here. No authoritative retirement notice was found either way; treat as **not applicable** rather than confirmed alive for this use case.

## 3. How would a developer get access, and is it stable enough for a PoC?

- Access model is **sponsorship + allowlisting**, not self-service signup: a Super Validator sponsors your validator node; the Canton Foundation's Tech & Ops Committee reviews (~2 weeks), then DevNet whitelisting takes another 2–7 days; TestNet needs additional tokenomics-committee approval [forum.canton.network](https://forum.canton.network/t/how-to-run-a-validator-on-devnet/8334), [canton.foundation/validators](https://canton.foundation/validators/).
- Fees: running your own validator on DevNet/TestNet needs test CC (Canton Coin) typically provided by the sponsoring SV or network faucets described in Splice validator-operator docs, not a public no-login faucet.
- Stability: allowlist entries and onboarding secrets are explicitly **time-bound** (DevNet allowlist resets ~every 3 months, TestNet ~3–6 months) [forum.canton.network](https://forum.canton.network/t/how-to-run-a-validator-on-devnet/8334) — this is explicitly built for iterative validator-operator testing, not a stable always-on PoC target a small frontend project can rely on indefinitely without a maintenance relationship with an SV.
- Net effect: this is not "unstable/experimental" in the sense of buggy, but it **is operationally unstable for an unaffiliated small PoC** — it requires an ongoing relationship with a sponsoring SV and periodic re-whitelisting, which is a materially different (and heavier) commitment than `docker compose up`.

## 4. Can a DAR be authored/uploaded without the local Daml SDK, by reusing a standard token package?

- **Compiling a custom Daml template still requires the local Daml SDK.** The Daml SDK page states plainly: **"The Daml compiler and Canton runtime require a JDK"** (Java 17+), installed locally via `dpm install` [docs.canton.network/sdks-tools/sdks/daml-sdk](https://docs.canton.network/sdks-tools/sdks/daml-sdk); the legacy docs.daml.com installation guide likewise requires **"JDK 11 or greater"** installed locally [docs.daml.com/getting-started/installation.html](https://docs.daml.com/getting-started/installation.html). There is no browser-based or hosted Daml build/compile service documented anywhere in the sources checked.
- This is true regardless of which ledger ultimately hosts the DAR (LocalNet, a self-run DevNet validator, or otherwise) — `daml build`/`dpm build` runs on the developer's machine.
- **Could the PoC avoid compiling anything new** by only exercising choices on an *already-deployed* standard token package? Partially, but not for this PoC's actual requirements:
  - Canton's global synchronizer ships a first-class, CIP-0056/`Holding`-compliant native token — **Canton Coin (Amulet)** — already active on every participant without deploying any custom DAR. A PoC that only needed "mint/hold/transfer *some* CIP-0056-compliant token" could in principle skip Daml compilation entirely by using Amulet.
  - However, this repo's spec/plan (`docs/superpowers/specs/2026-09-15-canton-token-poc-design.md`) explicitly requires a **custom** ERC-3643-style `IdentityRegistry` allowlist gating `Issue` and `TransferFactory_Transfer` — that logic does not exist in Amulet or in the vendored Splice token-standard interface packages themselves (those are interfaces/abstract packages, not a deployable allowlisted token). Implementing it requires a new template, hence a new DAR, hence the local Daml SDK.
  - Conclusion: **no, uploading the custom compliance-gated template in this PoC's design cannot avoid the local Daml SDK.** This is an important, non-negotiable finding, not a shortfall of research.

## 5. Node/React-compatible SDKs and packages

- **`@canton-network/wallet-sdk`** (npm, published under the `@canton-network` scope; source at [github.com/canton-network/wallet](https://github.com/canton-network/wallet), directory `sdk/wallet-sdk`) — the current, actively documented SDK for (a) key/party creation ("Authenticate and connect to a Canton synchronizer", external-party creation helpers) and (b)/(c) submitting `CreateCommand`/`ExerciseCommand`s and querying holdings/ACS via `sdk.ledger.prepare(...).sign(...).execute(...)` and `sdk.ledger.acsReader`/`sdk.tokenStandard`. Its own docs describe configuration as **either a `Provider` (auth bundled) or a `LedgerClientUrl` + `TokenProviderConfig`** [Wallet SDK Configuration](https://docs.digitalasset.com/integrate/devnet/wallet-sdk-configuration/index.html), i.e. the base URL and auth are both parameterized — LocalNet's `localNetStaticConfig.LOCALNET_APP_USER_LEDGER_URL` + `self_signed` unsafe-auth is only the LocalNet-convenience default (used in this repo's existing plan). Pointing `ledgerClientUrl` at a different participant with a real OAuth2/JWT `TokenProviderConfig` is exactly how the same SDK would be used against a real validator's Ledger API — the SDK itself is not LocalNet-locked. The remaining blocker is #2/#3 above: there is no such hosted URL to point it at without becoming (or paying) a validator operator.
- **`@daml/ledger`, `@daml/react`, `@daml/types`** — these are the *older* Daml JSON Ledger API v1 bindings. A Canton Network forum thread confirms **"@daml/ledger and @daml/react ... are no longer distributed with Canton 3.4"** because JSON Ledger API v1 is deprecated/removed as of Splice 0.5.0/Daml 3.4 in favor of JSON Ledger API v2 [forum.canton.network — "@daml/type, @daml/ledger, and @daml/react libraries for 3.x?"](https://forum.canton.network/t/daml-type-daml-ledger-and-daml-react-libraries-for-3-x/7884). They are **not** the right packages for a new PoC against current Canton Network. A community-maintained alternative, **`@c7-digital/ledger`** (npm), targets JSON Ledger API v2 directly, but it is third-party/unofficial, not a Canton Network or Digital Asset first-party package.
- Ledger API surface itself: **gRPC** and **JSON Ledger API v2** are both fully supported and equivalent in capability ("All calls available in gRPC Ledger API are also made available in JSON Ledger API v2") [docs.digitalasset.com — gRPC Ledger API Reference](https://docs.digitalasset.com/build/3.5/reference/lapi-proto-docs.html), [Get started with Canton and the JSON Ledger API](https://docs.digitalasset.com/build/3.5/tutorials/json-api/canton_and_the_json_ledger_api.html). The JSON API is the practical choice for a browser/Node app (no gRPC-web proxy needed), consistent with the existing plan's use of the JSON Ledger API.

## 6. What "wallet create/connect" concretely means on Canton

There is no local validator/participant process for a Node/React dev to allocate a party against unless one already exists somewhere:

- Every `PartyID` ("wallet") **must be hosted by a participant node** (a validator) — "Every interaction with the network must pass through a validator node ... that acts as a transaction gateway, key manager, and fee sponsor" [Validator Node Components](https://docs.canton.network/overview/reference/validator-node-components).
- Creating an "external party" (the wallet-SDK model used by this repo's plan) is a two-step topology transaction: `PartyToParticipant` (the party agrees to be hosted by a participant) and the participant's corresponding acceptance, exposed via validator admin endpoints like `/v0/admin/external-party/topology/*` and `/v0/admin/external-party/setup-proposal` [Create an External Party (Wallet)](https://docs.digitalasset.com/integrate/devnet/party-management/index.html); signing of the resulting topology/command payloads happens client-side with the wallet's private key (the "external party"/"BYOV" — bring your own validator/vault — pattern), while the actual submission and hosting are done by *some* participant.
- "Connect wallet" therefore concretely means: generate a keypair client-side → submit a party-allocation/topology request to *a specific participant's* Ledger/Admin API → that participant's operator (LocalNet's bundled validator, or a validator you or an SV-approved operator run) countersigns and hosts the party → the JWT/OAuth2 token used on subsequent Ledger API calls authenticates the calling application/user against *that participant*, scoped to acting for that party. Without a running local validator (LocalNet) or an already-provisioned external hosted participant, there is nothing to submit the party-allocation request *to* — this is the structural reason "no Docker, no local ledger process" and "connect wallet" are currently in tension for a fresh PoC.

## 7. Concrete, honest recommendation

**As of 2026-09-16, there is no currently-supported, open-signup, purely-hosted Canton sandbox that lets a Node.js/React-only developer skip running a local ledger process.** The only paths to a live Ledger API are: (a) LocalNet via Docker Compose (what the existing plan already uses), or (b) becoming/paying for a validator operator on DevNet/TestNet/MainNet, which is SV-sponsored, allowlisted, time-limited, and itself typically deployed via Docker/Kubernetes — i.e., strictly *more* infrastructure than LocalNet, not less. The official `cn-quickstart` explicitly dropped its DevNet bridge in July 2025, which is the clearest signal that even Digital Asset moved away from offering a lightweight hosted-DevNet path for quickstart-style apps.

Separately, this PoC's design requires a custom Daml template for the compliance allowlist, which requires the local Daml SDK (JDK) to compile regardless of hosting — this is unrelated to Docker and cannot be avoided by any hosted ledger choice.

**Closest workable compromise:** keep Docker, but shrink its footprint and blast radius, matching what the existing plan already does:
- Docker is unavoidable for the ledger (LocalNet), but it is a one-time `docker compose up` a Node/React developer never touches again after initial setup — exactly the existing plan's Task 1 approach (vendor `cn-quickstart`'s LocalNet compose module only, skip its sample app, `make setup` once, `docker compose ... up -d` once).
- The Daml SDK (`dpm`/JDK) is likewise a one-time local install needed only to compile the DAR (existing plan Tasks 2–5); once `daml/.daml/dist/*.dar` is built and uploaded (Task 6), day-to-day frontend work (Tasks 7–9) is pure `npm`/React/TypeScript against the already-running LocalNet JSON Ledger API — no repeated Daml or Docker interaction.

**What would need to change in the existing spec/plan if the user still insists on zero Docker:** the only honest option is to drop one of the three PoC features rather than pretend a hosted no-Docker ledger exists today:
- Either accept LocalNet+Docker as in the current plan (recommended — no change needed), **or**
- Descope to "read-only against a third-party MainNet RPC" (e.g., Canton Nodes' free endpoint) and drop mint/transfer of a *custom* token entirely, using only the pre-existing Amulet/CC holdings query as a demo — this satisfies "no Docker" but no longer demonstrates "mint a token via a Daml contract" as specified, and still costs real MainNet fees for any write operation, so it doesn't really satisfy the original three goals either.

Given that trade-off, this research recommends **no change** to `docs/superpowers/specs/2026-09-15-canton-token-poc-design.md` or `docs/superpowers/plans/2026-09-15-canton-token-poc.md` beyond adding a short note (in prose, not made here) that a hosted no-Docker alternative was investigated and found not viable as of 2026-09-16, with a link to this file, so a future reader doesn't re-derive the same research.

## Addendum (2026-09-16): "But isn't TestNet available?"

A separate query (via Canton's own AI docs assistant) reported: "Yes, TestNet is available ... requires IP whitelisting for access (no real value/Canton Coin involved). Access typically follows DevNet approval and requires application approval plus IP whitelisting." This is **true and does not change the conclusion above** — it confirms the network exists, not that it's a lightweight no-Docker sandbox. Reconciling the two:

- **TestNet is real and live** — it's the "production staging" network, sitting between DevNet and MainNet in the upgrade-rollout order [Deployment Progression / FAQ, per docs.canton.network, corroborated via web search of docs.canton.network content].
- Getting *onto* TestNet is **strictly heavier than DevNet, not lighter**: it still requires running your own validator node (Docker/Kubernetes — same as DevNet/MainNet), plus **GSF Tokenomics Committee approval**, applied for via `sync.global`, and that approval is explicitly gated on the applicant being **"within two weeks of production readiness"** — i.e. TestNet access is a pre-launch checkpoint for real applications, not a scratch space for exploratory PoCs [corroborated by multiple independent secondary summaries of the Canton docs' deployment-progression content; treat the "two weeks of production readiness" detail as secondary-sourced, not yet confirmed against the primary docs page verbatim].
- On top of the committee approval: IP allowlisting (2–7 day turnaround from a sponsoring SV), an onboarding secret, and the whole allowlist resets every 3–6 months — the same operational churn described in §3 above, now with an additional approval gate layered on.
- **Net effect: unchanged.** "TestNet is available" answers "does the network exist," not "can a Node/React developer reach it without Docker or an approval process." It cannot — TestNet access requires more process than DevNet, and DevNet already requires a self-hosted validator. The bottom line in this file stands.

## Addendum (2026-09-17): DevNet Scan API — real endpoints, empirically tested, currently blocked

A follow-up claim (from the user, sourced elsewhere) was that Canton's **Scan API** — a read-only network-state API (validator lists, token metadata, DSO info; intended per Splice's own docs for building "network analytic apps, block explorer apps, or financial accounting integrations" [Scan APIs — Splice docs](https://docs.dev.sync.global/app_dev/scan_api/index.html)) — has publicly-reachable DevNet endpoints, unlike the Ledger API (still IP-whitelisted per §2/§3 above). Two specific URLs were given:

- `https://scan.sv.dev.global.canton.network.digitalasset.com`
- `https://scan.sv-1.dev.global.canton.network.sync.global`

**Verified real, not fabricated.** Both resolve via DNS and complete a valid TLS handshake with a genuine Let's Encrypt certificate: `scan.sv.dev.global.canton.network.digitalasset.com`'s cert has `subject: CN=dev.network.canton.global`, SAN matching `*.sv.dev.global.canton.network.digitalasset.com`, issued by Let's Encrypt (`CN=YR1`), valid 2026-07-26 to 2026-10-24 — checked directly via `curl -v`, not asserted from a search result. Both gateways identify as `server: istio-envoy` (a Kubernetes/service-mesh ingress, consistent with an SV's own hosted infrastructure), and the digitalasset.com one sits behind `via: 1.1 google` (GCP-hosted).

**Empirically, every path tried returns 403, from this network's current outbound IP — tested 2026-09-17:**

```
GET https://scan.sv.dev.global.canton.network.digitalasset.com/api/scan/v0/splice-instance-names
  -> HTTP/2 403, body: "RBAC: access denied"
GET https://scan.sv.dev.global.canton.network.digitalasset.com/api/scan/v0/dso
GET https://scan.sv.dev.global.canton.network.digitalasset.com/v0/dso
GET https://scan.sv.dev.global.canton.network.digitalasset.com/api/scan/v0/state
GET https://scan.sv.dev.global.canton.network.digitalasset.com/api/scan/v0/synchronizers
GET https://scan.sv.dev.global.canton.network.digitalasset.com/api/scan/v0/domains
  -> all HTTP 403

GET https://scan.sv-1.dev.global.canton.network.sync.global/api/scan/v0/dso
GET https://scan.sv-1.dev.global.canton.network.sync.global/v0/dso
  -> both HTTP 403 (generic nginx "403 Forbidden" page, no RBAC-specific message)
```

`/v0/dso` is specifically significant: a Splice release-notes/docs snippet found via search states *"the SV app /v0/dso is currently public, but will require authorization as SV operator similar to most other SV app endpoints, with the public /v0/dso endpoint in the scan app available if you need to fetch DSO info"* — i.e. this is documented as the ONE endpoint meant to be open without SV-operator credentials. It returned 403 on both hosts regardless.

**Three possible explanations, none confirmed — do not treat any of these as settled:**
1. DevNet-wide IP allowlisting (already established in §2/§3 above for the Ledger API) may apply at the network edge for *all* traffic to an SV's infrastructure, including nominally-public Scan paths — i.e. "public" may mean "public once your IP is already allowlisted for DevNet," not "open to any internet host."
2. These two specific SV operators (Digital Asset's own `sv.dev` node, and a `sv-1` node under `sync.global`) may have configured stricter access than the documented default — Scan's public/private posture could be a per-operator gateway choice, not a network-wide guarantee.
3. The docs snippet's own wording ("is *currently* public, but *will* require authorization") reads as an in-progress lock-down; by 2026-09-17 that transition may already be complete, making the "public" claim stale.

**Bottom line:** the endpoints are genuine DevNet infrastructure, not invented — but as of 2026-09-17, from this environment's network path, they are **not** openly reachable, including the specific path Splice's own documentation calls out as the public one. This does not overturn §2/§3's conclusion (no open-signup path to Canton Network exists for this PoC); it narrows the earlier claim "no public read access at all exists anywhere on DevNet" to "at least these two SV's Scan gateways are not openly reachable from here, for reasons not yet confirmed." Retest from an already-allowlisted network/VPN, or from a different egress IP, before concluding either way.
